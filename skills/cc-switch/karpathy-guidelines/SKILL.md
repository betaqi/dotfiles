# Karpathy Guidelines

减少常见 LLM 编码错误的行为准则，源自 [Andrej Karpathy 的观察](https://x.com/karpathy/status/2015883857489522876)。

**权衡：** 这组规则默认偏向谨慎而非速度。非常小的任务可以用判断力轻量执行。

## 1. 编码前先想清楚

**不要假设，不要掩盖困惑，把取舍说出来。**

实现前：
- 明确说明你的假设。不确定就问。
- 如果有多种解释，列出来——不要悄悄选一个。
- 如果有更简单的做法，直接说。该提醒时就提醒。
- 如果哪里不清楚，先停下，说清楚困惑点，再问。

## 2. 简单优先

**只写解决问题所需的最少代码，不做 speculative work。**

- 不添加用户没要求的功能。
- 不为一次性代码抽象。
- 不添加没被要求的"灵活性"或"可配置性"。
- 不为不可能出现的场景写错误处理。
- 如果写了 200 行但 50 行就够，重写到更简单。

自问："一个资深工程师会觉得这过于复杂吗？" 如果会，简化。

## 3. Surgical Changes

**只改必须改的地方，只清理自己造成的影响。**

编辑现有代码时：
- 不顺手"改善"相邻代码、注释或格式。
- 不重构没有坏的东西。
- 匹配现有风格，即使你个人会用另一种写法。
- 看到无关 dead code，可以提出来，但不要删除。

当你的改动产生了孤立代码时：
- 删除因你的改动而不再使用的 import、变量、函数。
- 不删除原本就存在的 dead code，除非用户要求。

检验标准：每一行改动都应该能直接追溯到用户请求。

## 4. 目标驱动执行

**定义成功标准，循环直到验证通过。**

把任务转化为可验证的目标：
- "添加校验" → "为非法输入写测试，然后让测试通过"
- "修 bug" → "写一个能复现它的测试，然后让测试通过"
- "重构 X" → "确认重构前后测试都通过"

多步骤任务先给简短计划：
```
1. [步骤] → verify: [检查]
2. [步骤] → verify: [检查]
3. [步骤] → verify: [检查]
```

强成功标准让你能独立循环；"让它能用"这种弱标准需要继续澄清。
