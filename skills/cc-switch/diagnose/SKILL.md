# Diagnose

一套针对疑难 bug 的纪律。只有在能明确说明理由时才能跳过某个阶段。

探索代码库时，使用项目的领域词汇表来建立对相关模块的清晰心智模型，并检查你所涉及区域的 ADR。

## Phase 1 — 构建反馈循环

**这才是核心技能。** 其他一切都是机械性的。如果你有一个快速、确定性、agent 可运行的 pass/fail 信号来定位 bug，你就能找到原因——二分、假设验证、插桩都只是消费这个信号。如果没有，再怎么盯着代码看也没用。

在这里投入不成比例的精力。**要激进，要有创造力，不要放弃。**

### 构建方法——大致按此顺序尝试

1. **失败的测试**——在能触及 bug 的任何接缝处：unit、integration、e2e。
2. **Curl / HTTP 脚本**——对运行中的 dev server 发请求。
3. **CLI 调用**——用 fixture 输入，将 stdout 与已知正确快照做 diff。
4. **Headless 浏览器脚本**（Playwright / Puppeteer）——驱动 UI，对 DOM/console/network 做断言。
5. **重放捕获的 trace。** 把真实的网络请求/payload/事件日志保存到磁盘；在隔离环境中通过代码路径重放。
6. **一次性 harness。** 启动系统的最小子集（一个服务、mock 依赖），用一次函数调用行使 bug 代码路径。
7. **Property / fuzz 循环。** 如果 bug 是"有时输出错误"，跑 1000 个随机输入寻找失败模式。
8. **二分 harness。** 如果 bug 出现在两个已知状态之间（commit、数据集、版本），自动化"在状态 X 启动，检查，重复"以便 `git bisect run`。
9. **差异循环。** 对同一输入分别跑旧版本和新版本（或两种配置），diff 输出。
10. **HITL bash 脚本。** 最后手段。如果必须由人来操作，用 `scripts/hitl-loop.template.sh` 来引导他们，使循环仍有结构。捕获的输出反馈给你。

构建正确的反馈循环，bug 就已经修了 90%。

### 迭代循环本身

把循环当作产品。一旦有了 _一个_ 循环，问：

- 能更快吗？（缓存 setup、跳过无关初始化、缩小测试范围。）
- 信号能更锐利吗？（对具体症状做断言，而不是"没 crash"。）
- 能更确定性吗？（固定时间、seed RNG、隔离文件系统、冻结网络。）

一个 30 秒的 flaky 循环比没有好不了多少。一个 2 秒的确定性循环是调试超能力。

### 非确定性 bug

目标不是干净复现而是**更高的复现率**。把触发循环跑 100 次，并行化，加压力，缩小时间窗口，注入 sleep。一个 50% flake 的 bug 是可调试的；1% 不行——持续提高复现率直到可调试。

### 当你确实无法构建循环时

停下来，明确说出来。列出你尝试过的方法。向用户请求：(a) 能复现的环境的访问权限，(b) 捕获的制品（HAR 文件、日志 dump、core dump、带时间戳的录屏），或 (c) 添加临时生产插桩的许可。**不要**在没有循环的情况下进入假设阶段。

在你相信你的循环之前，不要进入 Phase 2。

## Phase 2 — 复现

运行循环。看着 bug 出现。

确认：

- [ ] 循环产生的是**用户**描述的失败模式——不是恰好在附近的另一个失败。错误的 bug = 错误的修复。
- [ ] 失败在多次运行中可复现（或对非确定性 bug，复现率足够高到可以调试）。
- [ ] 你已捕获确切症状（错误信息、错误输出、慢的时间点），以便后续阶段可以验证修复确实解决了它。

在复现 bug 之前不要继续。

## Phase 3 — 假设

在测试任何假设之前，先生成 **3-5 个排序后的假设**。单假设生成会锚定在第一个看似合理的想法上。

每个假设必须**可证伪**：说明它做出的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更严重。"

如果你说不出预测，这个假设就是直觉——丢弃或磨锐它。

**在测试前把排序列表展示给用户。** 他们通常有领域知识可以即时重排（"我们刚部署了对 #3 的改动"），或知道哪些假设已被排除。低成本检查点，节省大量时间。不要阻塞在这一步——如果用户不在，按你的排序继续。

## Phase 4 — 插桩

每个探针必须对应 Phase 3 中的一个特定预测。**一次只改变一个变量。**

工具偏好：

1. **Debugger / REPL 检查**——如果环境支持。一个断点胜过十条日志。
2. **有针对性的日志**——放在能区分假设的边界处。
3. 永远不要"把所有东西都 log 出来然后 grep"。

**给每条 debug 日志打标签**，用唯一前缀，如 `[DEBUG-a4f2]`。最后清理变成一次 grep。没标签的日志留着；有标签的日志必须删除。

**性能分支。** 对于性能回退，日志通常不对。改用：建立基线度量（计时 harness、`performance.now()`、profiler、query plan），然后二分。先度量，再修复。

## Phase 5 — 修复 + regression test

**在修复之前**写 regression test——但前提是存在**正确的接缝**。

正确的接缝是指测试能在调用点行使**真实 bug 模式**的位置。如果唯一可用的接缝太浅（bug 需要多个调用者但只有单调用者测试，单元测试无法复现触发链），在那里做 regression test 会给人虚假信心。

**如果不存在正确的接缝，这本身就是发现。** 记录下来。代码库的架构正在阻止 bug 被锁定。把这个标记给下一阶段。

如果存在正确的接缝：

1. 把最小化复现转化为该接缝处的失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 对原始（未最小化的）场景重新运行 Phase 1 的反馈循环。

## Phase 6 — 清理 + 复盘

宣布完成前必须确认：

- [ ] 原始复现不再复现（重新运行 Phase 1 循环）
- [ ] Regression test 通过（或接缝缺失已记录）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（grep 前缀）
- [ ] 一次性原型已删除（或移到明确标记的 debug 位置）
- [ ] 被验证正确的假设已写在 commit / PR 消息中——让下一个调试者能学习

**然后问：什么能防止这个 bug？** 如果答案涉及架构变更（没有好的测试接缝、调用者纠缠、隐藏耦合），带着具体信息移交给 `/improve-codebase-architecture` skill。在修复完成**之后**提出建议，而不是之前——你现在比开始时掌握更多信息。
