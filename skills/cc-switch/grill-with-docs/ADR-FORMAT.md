# ADR 格式

ADR 存放在 `docs/adr/`，使用顺序编号：`0001-slug.md`、`0002-slug.md`，以此类推。

`docs/adr/` 目录按需创建——只在第一个 ADR 需要时才建。

## 模板

```md
# {决策的简短标题}

{1-3 句话：背景是什么，我们决定了什么，以及为什么。}
```

就这些。一个 ADR 可以只是一段话。价值在于记录**做了**什么决策以及**为什么**——不在于填充模板的每个部分。

## 可选部分

只在确实有价值时才添加。大多数 ADR 不需要这些。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）— 决策被重新审视时有用
- **Considered Options** — 只在被否决的替代方案值得记住时
- **Consequences** — 只在非显而易见的下游影响需要被指出时

## 编号

扫描 `docs/adr/` 中现有的最高编号，加一。

## 何时提供 ADR

以下三个条件必须全部满足：

1. **难以撤回** — 事后改变主意的代价不小
2. **没有上下文会令人费解** — 未来的读者会看着代码疑惑"他们到底为什么这么做？"
3. **是真实权衡的结果** — 存在真正的替代方案，而你基于具体原因选择了一个

如果决策容易撤回，跳过——反正你会直接改。如果不令人费解，没人会疑惑。如果没有真正的替代方案，除了"我们做了显而易见的事"没什么可记录的。

### 什么够格

- **架构形态。** "我们使用 monorepo。" "写模型是 event-sourced 的，读模型投影到 Postgres。"
- **上下文之间的集成模式。** "Ordering 和 Billing 通过领域事件通信，不用同步 HTTP。"
- **带有锁定效应的技术选型。** 数据库、消息总线、认证提供商、部署目标。不是每个库——只是那些换掉需要一个季度的。
- **边界和范围决策。** "Customer 数据归 Customer 上下文所有；其他上下文只通过 ID 引用。" 明确的"不做什么"和"做什么"一样有价值。
- **对显而易见路径的刻意偏离。** "我们用手写 SQL 而不是 ORM，因为 X。" 任何合理的读者会假设相反做法的情况。这能阻止下一个工程师"修复"一个本来就是刻意为之的东西。
- **代码中不可见的约束。** "因为合规要求我们不能使用 AWS。" "响应时间必须低于 200ms，因为合作方 API 合约。"
- **被否决的替代方案（当否决原因不显然时）。** 如果你考虑了 GraphQL 但因为微妙的原因选了 REST，记录下来——否则六个月后有人会再次提议 GraphQL。
