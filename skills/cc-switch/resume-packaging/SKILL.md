# resume-packaging

把项目事实转化为可写进中文技术简历的项目亮点和 bullet。

核心原则：**project-analysis 负责事实，resume-packaging 负责表达。**

- `project-analysis`：事实层。负责架构、模块、数据流、工程特征、复杂点、证据。
- `resume-packaging`：表达层。基于事实提炼"可包装亮点"，生成真实、克制、可追问的简历 bullet。

本 Skill 不重新做完整项目分析。它优先消费 `project-analysis` 的事实产物；如果没有事实产物，可以基于用户描述生成"待确认版"建议。

---

## 触发场景

当用户想把项目经历转成简历内容时使用，包括：

- "根据这个项目包装简历"
- "根据代码补简历"
- "这个项目怎么写到简历里"
- "帮我改简历项目部分"
- "项目写得太平，帮我改得有技术含量"
- "根据 JD 优化项目描述"
- "把项目亮点写成简历 bullet"

不要因为以下请求自动触发：

- 写代码、加功能、改 bug、重构
- "帮我优化这个项目"（指优化代码，不是优化简历描述）
- "这个项目有什么问题"（指代码问题，不是简历表述问题）
- "帮我改一下这个"（指改代码或文档，不是改简历）
- 普通 code review、PR 评审
- 讨论技术方案、架构设计
- 只有出现"简历""resume""JD""面试""bullet"等明确关键词时才触发

---

## 输入优先级

优先使用以下信息源，顺序从高到低：

1. `project-analysis` 输出：项目事实、模块、架构、数据流、复杂点、证据。
2. 用户简历：确认当前项目在简历中的已有表述、时间、技术栈、职责。
3. 用户个人职责说明：确认哪些事情是用户本人做的。
4. JD：用于调整关键词和表达优先级。
5. 用户补充描述：只能作为待确认信息，除非用户明确确认。

`project-analysis` 输出的判定规则：

1. 当前对话中存在明确的 `project-analysis` 结果，并包含项目事实、模块、架构、数据流、复杂点、证据等结构化内容。
2. 用户粘贴了 `project-analysis` 的输出内容。
3. 当前工作区存在 `project-analysis-report.md`。

约定事实产物文件：

- `project-analysis-report.md`

如果没有找到 `project-analysis` 输出：

- **首选路径**：询问用户是否已有项目分析结果。如果没有，建议用户先运行 `project-analysis`。
- **轻量级兜底路径**：如果用户不愿或无法运行 `project-analysis`（例如项目不在当前工作区），可以基于以下信息直接生成待确认版建议：
  - 用户提供的项目简介和职责
  - 用户主动复制粘贴的代码片段、配置、文档
  - 用户对技术细节的回答
  - 所有未经验证的内容必须标注 `【待确认：未经过 project-analysis 验证】` 或更具体的原因
- 兜底路径必须告知用户：未经验证的建议可能存在事实错误，建议在写入简历前自行确认。

## 职责边界

本 Skill 可以做：

- 从事实中提炼适合写入简历的技术亮点。
- 判断亮点是否有足够证据支撑。
- 将事实表达成中文技术岗简历 bullet。
- 给出保守版和增强版。
- 标记个人贡献、指标、业务价值中的待确认点。
- 根据 JD 调整 bullet 的关键词和排序。
- 对亮点的简历竞争力做校准评级。

本 Skill 不应该做：

- 凭空推断架构设计、性能收益、用户规模、业务结果。
- 把"项目存在某能力"写成"用户主导实现该能力"。
- 把简单接入、调用、配置包装成复杂架构设计。
- 未经用户确认就写具体数字、百分比、QPS、耗时、成本下降。
- 修改整份简历或影响其他项目，除非用户明确要求。

---

## 竞争力校准

对每个亮点给出简历竞争力评级，帮助用户判断这个点在同级别岗位中的含金量。

| 评级 | 含义 | 例子 |
|---|---|---|
| 标配 | 大多数同岗候选人都能做到，不构成差异 | 用 Redis 做缓存、REST API 增删改查 |
| 加分 | 有一定技术含量或独特性，能拉开差距 | 自研状态管理方案、跨 5 个模块的异步链路治理 |
| 亮点 | 显著高于同级别预期，能主导面试方向 | 设计并落地一套完整的权限体系覆盖 200+ API、从 0 搭建 LLM 推理管线 |
| 有争议 | 技术上存在取舍，面试官可能不认可 | 强依赖某一框架的非标用法、性能优化但牺牲可维护性 |

**评级说明：**
- 评级基于常见技术栈的行业惯例判断，不是"查过市场数据"，仅供参考。
- 同一点在不同级别岗位中评级不同。例如"用 Redis 做缓存"在 3-5 年经验是标配，在更高职级是减分项（应该讲清楚缓存策略而非只提用了 Redis）。
- 如果可以确定用户目标级别（来自简历或用户描述），按目标级别校准；否则默认为 3-5 年经验的社招水准。
- **兜底模式下**（未经过 project-analysis），竞争力评级降级为"基于用户描述推断"，不保证与真实代码一致的准确度。
- **评为"有争议"的亮点**：要么降级表达以避开争议点，要么准备正反对比说辞并在面试中主动引导（"这个方案有争议，具体来说……"）。不建议毫无准备地直接写入简历。

## 执行流程

### 1. 读取事实材料

优先读取或使用 `project-analysis` 输出，提取：

- 项目名称和业务目标
- 技术栈
- 核心模块
- 架构和数据流
- 工程复杂点
- 可验证证据，如文件路径、模块名、接口、配置、README、测试、日志说明

如果用户提供简历路径，读取简历并匹配当前项目。匹配依据包括项目名称、时间、技术栈、模块描述和业务功能。输出匹配信心：高 / 中 / 低。

如果用户提供 JD，提取 JD 关键词，只用于排序和措辞优化，不用于虚构经历。

**JD 技术栈与实际技术栈冲突处理：** 如果发现 JD 要求的技术栈（如 Java）与项目实际技术栈（如 Python）不匹配，必须向用户指出："JD 要求的技术栈与项目实际技术栈不一致，建议注意岗位匹配度风险。" 不要自行调整词汇来掩盖这个冲突。

如果用户要求英文输出，同时提取用户的英文简历（如有），保持英文风格一致。

### 2. 提炼可包装亮点

从事实材料中筛选"可包装亮点"。一个亮点应至少满足其中两项：

- 有明确技术动作：设计、实现、优化、封装、接入、迁移、治理、排查。
- 有工程复杂度：跨模块、异步链路、状态管理、性能、稳定性、权限、安全、数据一致性、可观测性。
- 有可验证证据：代码模块、接口、配置、测试、文档、项目分析引用。
- 能对应用户职责：用户明确做过或可向用户确认。
- 能产生简历价值：提升可维护性、扩展性、稳定性、交付效率、体验、协作效率。

不要把纯功能清单直接当成亮点。应从"做了什么功能"进一步提炼为"解决了什么工程问题"。

### 3. 确认个人贡献

对每个亮点标记个人贡献状态：

| 状态 | 含义 |
| --- | --- |
| 已确认 | 用户明确说过本人负责，或简历中已有对应职责 |
| 需用户确认 | 项目事实存在，但不确定是否由用户本人完成 |
| 无法判断 | 事实与用户职责无法建立关系 |

对于"需用户确认"和"无法判断"的亮点，bullet 中必须使用 `【需确认：...】` 标记，或放入确认问题清单。

### 4. 生成简历 bullet

每个亮点生成 1-2 条 bullet，默认不要过量输出。每条 bullet 包含：

- **保守版**：只写事实可支撑、个人贡献明确或措辞安全的内容。
- **增强版**：在事实基础上加入工程价值或业务价值，但必须标记未确认部分。
- **使用条件**：说明增强版需要用户确认什么。
- **事实依据**：引用来自 `project-analysis` 的证据或用户确认来源。
- **竞争力评级**：标配 / 加分 / 亮点 / 有争议（针对目标级别）。

中文 bullet 写法要求：

- 中文技术岗简历风格。
- 动作词开头：负责 / 设计 / 实现 / 优化 / 构建 / 接入 / 封装 / 推动 / 主导 / 迁移。
- 结构：动作 + 技术/方案 + 结果/价值。
- 避免空话，如"显著提升""大幅优化""高效赋能"，除非有证据。
- 没有可确认指标时，不写百分比、规模、耗时、成本收益。
- 不能把团队成果默认写成个人主导。

### 5. 分级建议

对每个亮点给出写入建议：

| 状态 | 说明 |
| --- | --- |
| 可直接写入 | 事实清楚，用户贡献明确，面试可追问 |
| 需确认后写入 | 项目事实成立，但个人贡献、指标或价值需确认 |
| 不建议写 | 证据弱、职责不明、容易被问穿 |
| 适合面试展开 | 可以口头讲，但写进简历价值不够高 |
| 需要补习后再写 | 技术点真实存在，但用户需要先能讲清楚 |

## 输出模式

| 模式 | 触发条件 | 输出内容 |
|---|---|---|
| 完整模式（默认） | 用户要求包装简历、改简历项目部分 | 全部五个章节 |
| 精简模式 | 用户说"只要交接块""给面试准备用""精简版" | 只输出「推荐写入顺序」+「结构化交接块」 |

精简模式适用于：用户明确要串联 interview-coaching，不需要完整的亮点分析过程，只需要最终结论和结构化数据。

---

## 简历文件处理

- 默认只输出 markdown 建议，不修改文件。
- 用户提供简历路径时，可以读取并只针对当前项目给建议。
- 用户明确要求修改简历文件时，先说明"只会修改当前项目对应部分"，再操作。
- 如果无法匹配当前项目，必须询问用户简历中哪个项目对应当前分析结果。

## 输出格式

### 一、事实输入概况

| 字段 | 内容 |
| --- | --- |
| 项目分析来源 | 文件 / 用户粘贴 / 未提供（兜底模式） |
| 项目名称 |  |
| 简历对应项目 |  |
| 匹配信心 | 高 / 中 / 低 / 未匹配 |
| 用户个人职责 | 已确认 / 待确认 / 未提供 |
| JD 使用情况 | 已提供 / 未提供 |
| 输出语言 | 中文 |
| 目标级别（如可推断） | 0-2年 / 3-5年 / 5-10年 / 10年+ / 不确定 |

### 二、可包装亮点

按推荐优先级输出：

#### 亮点名称

- 建议状态：可直接写入 / 需确认后写入 / 不建议写 / 适合面试展开 / 需要补习后再写
- 竞争力评级：标配 / 加分 / 亮点 / 有争议
- 个人贡献：已确认 / 需用户确认 / 无法判断
- 事实依据：引用 `project-analysis` 中的模块、证据或用户确认
- JD 关键词：如有 JD，则列出匹配关键词

保守版：

- 负责 / 设计 / 实现 ...

增强版：

- 负责 / 设计 / 实现 ...【需确认：具体指标、业务结果或个人职责】

增强版使用条件：

- 用户需要确认的事实

### 三、推荐写入顺序

列出最建议放入简历的 3-5 条 bullet，并说明排序理由。

### 四、需要用户确认的问题

只列出会影响真实性或面试可追问性的问题，例如：

1. 这个模块是否由你本人负责？
2. 是否有可确认的性能、稳定性、效率或业务指标？
3. 你在该方案中是主导、核心开发、参与开发，还是维护优化？
4. 【请确认】你想优化的是多个已有项目中的哪一个？如果整份简历中有多个项目，先确认目标项目与当前分析结果的对应关系。

### 五、结构化交接块

供 `interview-coaching` 等下游 skill 消费。只输出已确认和需确认的亮点，不输出"不建议写"的内容。

```yaml
resume_packaging_handoff:
  project_name:
  target_level: 0-2年 / 3-5年 / 5-10年 / 10年+ / 不确定
  highlights:
    - title:
      bullet_conservative:
      bullet_enhanced:
      ownership: 已确认 / 需用户确认 / 无法判断
      competitiveness: 标配 / 加分 / 亮点 / 有争议
      status: 可直接写入 / 需确认后写入 / 需要补习后再写 / 适合面试展开
      risk_points:
        - 面试中可能被追问穿的点
      evidence:
        - 来自 project-analysis 的证据引用
      needs_study:
        - 需要补习才能讲清楚的知识点（仅 status 为"需要补习后再写"时填写）
  unconfirmed_questions:
    - 需要用户确认的问题
```
