# Scoped Change

改东西时的工作方式。常驻规则（如实汇报、高影响操作确认）不在这里，见 CLAUDE.md。

小任务轻量执行，不要为了走流程而走流程。

## 1. 先理解，再动手

- 改之前先读相关代码和文档，确认现状，不凭印象。
- 涉及版本、API、依赖行为等当前状态：查证，不靠记忆。

## 2. 歧义：按场景决定问还是做

| 情形 | 做法 |
|---|---|
| 歧义小，或做错容易回退 | 选最合理的解释，写明假设，继续做 |
| 歧义大且代价高（大改动、批量、不可逆） | 动手前问，一次问清 |
| 无人值守 / 后台 / 定时 | 不阻塞提问；写明假设，继续做 |
| 无人值守且遇到不可逆决策 | 做完准备工作，列出决策点，停下 |

有多种合理解释时，不要悄悄选一个，要让用户看到你选了哪个。有更简单的做法就直接说。

## 3. 改动范围：只做被要求的事

- 每处改动都应能追溯到用户请求。
- 不顺手重构、改格式、改注释、升级依赖。
- 匹配现有风格，即使你会换一种写法。
- 发现无关问题（dead code、潜在 bug）：汇报时提出，不要直接改。
- 只清理自己改动造成的残留（不再使用的 import、变量、函数）。

## 4. 简单优先

- 用最少的代码解决问题。
- 不为一次性需求抽象，不加没人要的配置项、扩展点、兼容层。
- 不为不可能的场景写防御代码；只在系统边界（用户输入、外部 API）校验。
- 自检：资深同事会觉得过度吗？会就简化。

## 5. 验证：用证据说完成

开工前先定义"怎么算做完"，尽量可检查：

- 修 bug：先复现，再修，再确认复现消失。
- 加功能：测试或实际运行能验证。
- 重构：改前改后行为一致，测试都通过。
- 没有测试：写最小验证或实际运行一遍；确实无法验证就明说。
- 不把"代码看起来对"当作"已验证"。

大任务先给 3–5 步计划，每步附验证方式：

```
1. [步骤] → verify: [检查]
2. [步骤] → verify: [检查]
```

## 6. 编码细则

- 优先用项目已有的库；新增依赖要说明理由。
- 不为让测试通过而削弱或删除断言。
- 一个提交一件事；不擅自 commit/push，除非被要求。
- 不吞异常；不硬编码密钥；注意注入和未校验输入。
- 交付前通读自己的 diff，删掉调试代码、无关改动和多余注释。

## 7. 交付时的汇报要点

在 CLAUDE.md 的如实汇报基础上，补充：做了什么、怎么验证的、做了哪些假设、没做或有风险的部分、发现的无关问题。几句话即可，不要流水账。
